# Adversarial review

Review scope: the delivered token, fee/voting implementations, transparent proxy, CREATE2 deployment helper, dependencies, and actual v4 delta settlement. This is a separate adversarial pass by the implementing contributor, not an independent contributor's audit. No production transaction, funded wallet, or live fork was used.

## Confirmed risks and decisions

| Finding | Impact / evidence | Resolution or responsibility |
| --- | --- | --- |
| Shared deployment helper allowed front-running of initial price | Price and fee-tier configuration is outside the proxy constructor hash. A stranger could previously consume a mined salt with the victim's exact proxy initialization and a different pool price. | Fixed: `deployHook` requires the configured application owner as its caller. Owner participates in the proxy initialization hash. `test_minedDeploymentCannotBeFrontRunByChangingPrice` proves refusal. |
| Pre-swap fee on an unfilled IMD amount | Charging the requested amount before price-limit execution can overcharge a partial fill. | Fixed: afterSwap requires exact consumption of the adjusted IMD specified amount, otherwise rolls back the whole swap. Paper-specified partial fills use actual IMD deltas. Separate success and rollback tests cover both. |
| Recipient rounding could lose fee units | Independent rounded recipient calculations need not sum to the total. | Fixed: dev receives the remainder after rounded orders allocation. Split fuzzing and sequence invariants prove conservation, including 0/200 shares. |
| Reentrant token can forge voting sequence or enter during fee payout | External ERC-20 calls may call public functions before the original action completes. | Namespaced guard covers post, burn, fee-bearing callbacks, and all administrative mutations. Posting reserves the ID before transferring and reverts atomically. Hostile-token tests exercise fee payout, posting, and burning reentry. |
| Transfer can return false or deliver fewer paper units | An event could report more burned votes than actually reached dead. | SafeERC20 and dead-address balance differences reject false and short transfers; tests verify rollback of ID and balances. Launch Paper itself has exact transfers. |

A paper-only fresh pool does not physically hold IMD. | Mandatory same-swap payout excludes accumulated-claim fallback. The hook explicitly reverts if backing is insufficient. | Owner-set IMD/USD is discretionary and can become stale | No reviewed chain-readable source was supplied; the owner can change the quote or make posting uneconomic. Owner is responsible for freshness and a sensible fee. Users approve exact intended amounts. There is no automatic price heartbeat or bound. |
| Transparent upgrades can change economics | New code can return arbitrary fee or liquidity deltas, change ownership rules, or use existing token approvals. ## Callback and delta analysis

Every one of the ten callback functions checks the namespaced PoolManager address. The full unauthorized-callback test checks returned revert bytes, including unused callbacks and afterSwap. The single pool is bound by beforeInitialize to the configured paper token and fixed IMD; only the initializer helper or application owner can initialize it. Pool ID validation prevents use for a different fee/spacing/key, and rebinding is rejected. Initialization and helper deployment are atomic, so a reverted pool initialization cannot leave a partially configured proxy.

All fourteen address flags and permission fields match. The liquidity and donation return deltas are zero; lifecycle tests donate and remove the real position without charging fees. beforeSwap returns zero for paper-specified modes, and only a positive IMD specified fee otherwise. Exact-input fee is 2% of the gross budget and cannot cancel the entire AMM swap. Exact-output IMD gross-up requests the AMM amount necessary to provide the caller's original net output. afterSwap returns a positive fee only for the unspecified IMD leg. It returns zero when beforeSwap already charged, preventing double fees. No callback uses a caller-selected recipient, rate, target, or router-supplied voter identity.

`manager.take(IMD, recipient, amount)` creates a hook debit for each payment. The sum of these debits is exactly the positive returned IMD fee delta. The manager's post-callback accounting credits that delta to the hook and subtracts it from the caller's delta. The test router uses `sync -> transferFrom -> settle` for debts and `take` for credits; its unlock completes only when every manager delta is zero. Unit tests compare trader, manager, both wallets, and the hook after each swap. The stateful invariant interleaves all four swap modes, all valid splits, posts, and burns, then checks aggregate expected fees/burns, total supply, no hook balances, no remaining hook/router deltas, zero nonzero-delta count, and a locked manager.

There is no arbitrary AMM replacement, full-input NoOp return, LP fee override, rescue function, claim balance, payable hook entry, unbounded on-chain voting loop, or `tx.origin` authorization. Salt search is bounded to 200,000 candidates and intended for off-chain simulation; it is not a swap path. The explicit signed bounds reject int256 minimum and amounts outside int128 before encoding return deltas.

## Upgrade analysis

OpenZeppelin Contracts 5.4.0 supplies the transparent proxy and ProxyAdmin. The custom proxy adds no external selectors. It fixes ProxyAdmin initial ownership in its creation code, requires all fourteen bits, and requires the exact initialization selector and ABI length. The implementation constructor disables its initializer; proxy initialization runs in the constructor and cannot be seized between transactions. A plain user, application owner, or direct call from the dev wallet cannot invoke the proxy upgrade path. Only the proxy's ProxyAdmin contract can; only its owner can instruct it. The ProxyAdmin contract cannot accidentally call application functions through the transparent proxy.

Application state uses the computed ERC-7201 namespace, independently verified in the upgrade test. That test snapshots the entire occupied namespace region, upgrades through ProxyAdmin, compares the raw slots, and then trades, burns against an old ID, and posts a new ID. The old split survives even though the fresh-V2 default differs. Attempting to initialize again during an upgrade reverts the upgrade transaction and preserves the old implementation. V2 adds no slots and changes only `_defaultSplit`. Initializable uses its own namespace; ERC-1967 proxy slots are disjoint.

## Verification and remaining release work

Foundry unit, fuzz, and stateful tests run without RPC or environment reads against real local PoolManagers. Default fuzzing uses 256 inputs per fuzz test; the invariant runs 64 sequences of depth 32 with `fail_on_revert = true`. The expanded suite contains 80 passing tests, with no skips. Compiler 0.8.26 build and format checks pass. A gas-report run also passed before the final two regression tests were added.

The gas report measured V1 beforeSwap up to approximately 89,198 gas and afterSwap up to 79,494 gas across success/failure paths and fixtures. These are local measurements, not a promise for mainnet token behavior. Production runtime sizes: Paper 1,723 bytes, both implementations 11,883 bytes, proxy 1,073 bytes, deployment helper 10,022 bytes; all below EIP-170. Init code also stays below EIP-3860 limits.

Foundry lint warnings were examined: guarded/revert-bounded integer casts, ABI concatenation for deterministic creation bytes, events following guarded external calls, manager initialization's unused return tick, and exact token-delivery comparison are intentional. Access modifiers preceding `nonReentrant` only read namespaced storage and make no external calls. These warnings are not silently represented as an independently clean static-analysis report. Slither, Mythril, formal verification, live fork testing, external audit, and a bug bounty were not run.

Before mainnet release an independent contributor must review this code and the two requirement conflicts, verify the live manager/IMD and production router settlement, approve the IMD/USD maintenance procedure and spot-price limitation, approve launch price/ranges/funding/LP custody, rehearse with live chain state, verify deployed code and ownership, and arrange upgrade/parameter/event monitoring. This repository is a locally checked deliverable, not evidence that these release steps occurred.
